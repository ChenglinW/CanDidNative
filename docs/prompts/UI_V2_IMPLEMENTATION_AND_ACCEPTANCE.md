## 3. 必须完成的真实业务链路

### A. 录音自动处理

设备同步或手机备用录音完成 → 上传与持久化 → 最终转写 → 复盘 → 带来源的动态记忆与表达积累 → 向同一个 Chat 主动写入结果消息及录音引用 → 刷新首页与录音列表。

用户不必再说“帮我复盘”。消息到达不强制展开聊天，也不新增未要求的首页未读样式。Chat 引用、首页卡片、列表和详情使用同一个 recording_id。失败如实显示阶段；重试、重复同步、断线恢复和服务重启不能重复生成记录、记忆或主动消息。

### B. 会前准备

Chat 识别准备意图 → 结合已知资料，只补问对象、目标、时间、顾虑中真正缺少且必要的信息 → 生成完整报告并保存准备包 → 在 Chat 展示准备包卡片 → 首页按规则显示同一份准备包。

两个入口使用相同 preparation_package_id 和版本。全文页面只读、只有返回，保持返回前的聊天状态。时间未知可以继续准备；相对时间按用户时区解析。准备包内容应包含目标、对象背景、相关事实与依据、提纲、关键问题、表达建议、顾虑和待核实项。

### C. 长期上下文与记忆

一个长期 Chat 需要可检索用户所有历史录音及长期资料，首页三条上限不限制检索。按问题检索相关片段，保留原文、时间戳、文件与版本依据；区分不同客户、事项和说话人，不能因单线程而串事实。长对话摘要后仍保留目标、约束、未完成事项和来源定位。

长期资料与录音衍生记忆分别管理；用户修正有版本与来源，不能被后续模型静默覆盖。跨场新个人结论按已确认规则处理。SOUL.md、固定 Skill 索引、按需加载、Monid 公司调研、任务排队、取消、重连和恢复在新结构下继续工作。

### D. 资料与语音

文件上传必须完成实际读取、解析、保存和 Agent 检索引用；覆盖原型开放的文件类型，不能只保留文件名。检查 PDF 中文、多页、表格、扫描件、加密及损坏等结果，失败给出对应原因和可执行恢复方式。

沿用已配置的文本、DashScope ASR/TTS 与 Monid 接口，不擅自换模型。验证实时字幕、准确转写、时间戳、中英粤语混合与保留粤语原话、最终分人、说话人改名、本人认领、TTS 播放暂停停止及打断。只在 SDK 实际提供实时音频时接入录音豆实时字幕。

## 4. 测试方法与测试集

先把产品要求整理成“要求 → 页面入口 → 接口／状态 → 测试 → 结果证据”的可追踪清单。调整旧测试以符合新产品，保留仍有意义的断言；不要为了通过测试降低验收标准。

自行生成或寻找合适测试集，保存可重复运行的文件、来源／许可、预期结果和运行方式。至少包括：

- 全新用户、仅资料、仅录音、完整数据；销售与面试；多个客户事实可明确区分；超过三场历史录音的检索；长对话压缩后回忆与引用。
- 准备信息齐全和缺失、时间待定、多份准备包、相对时间、修改、结束场次；Chat 与首页 ID 一致，返回状态保留。
- 实际中文产品资料、报价／服务范围、简历／JD；PDF、原型开放的其他格式；空文件、损坏、扫描、加密及大小边界。检查 Agent 能回答资料中的可核对事实，并正确引用。
- 普通话、英语、粤语及混合；单人、多人轮流、长停顿、噪声、少量重叠；命名、本人认领；录音、语音消息和连续对话的区别。
- TTS 中途开口、短暂停顿抢接、快速重复操作、按住后松开／上滑、权限等待期间松手、切后台、断网重连、任务取消、排队、重复上传和后端重启。
- 来源修订后结论失效、用户修正保留、跨场确认、不同用户数据隔离、空资料时不编造依据。

使用合成音频时注明它验证了哪些能力；不要把合成说话人结果当成真实人群准确率。为 ASR 记录有参考文本的质量结果，为流式链路记录收音、ASR 就绪、首次文字、最终文字、Agent 首字、TTS 首音等时间点，区分客户端、代理网络和模型耗时。

分层执行后端测试、原生逻辑测试、XCUITest、原生截图检查，以及真实 App → 后端 → 已配置服务的端到端用例。Mock 用于可重复故障测试，真实接口用于验证实际接入，两者分别记录。测试录音到 Chat、准备到首页、资料到回答等完整闭环，不能以单个接口成功代替整条链路。

以模拟器承担主要 UI 和回归测试，真机补麦克风、回声、VAD、打断与生命周期。手机自动锁屏或暂不可用时继续完成模拟器、后端和接口部分；需要硬件的结论明确记为待验证。不要用手机屏幕共享干扰麦克风测试。没有安克设备就完成 SDK 代码、状态和协议测试，列明设备实测缺口。
