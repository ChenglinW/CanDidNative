# Monid 综合测试与触发评价

> 这是修复前基线评估；后续已完成修复和真实验收，见 [修复交付记录](FIX_REPORT.md)。

日期：2026-10-16。版本基线：`4251cd1`。本轮执行测试与评估，没有修改、部署或推送产品代码。

## 结论

四类基础能力——搜索、正文读取、公司档案、视频字幕——均有真实成功回执，但整体尚不能算完整可用。最需要修的是首页准备流程的权限与衔接、供应商错误解析及失败恢复；暂不需要换平台或增加大量连接器。

特别是首页默认助手：用户明确要求“先联网读取官网再保存准备包”，系统仍只查本地资料并保存了准备包。后台任务显示完成不代表满足了完整需求。

## 测试范围与证据

- 对四个已登记端点重新 inspect，核对实际输入规范、健康状态及价格。
- 本机 24 个接口／缓存场景，含无效链接、404、网络失败及复测；另在生产服务器的隔离临时数据库复测 3 个场景，并直接观察 2 个 HTTP 错误响应。
- 云端实际文本模型运行 11 个 Agent 场景，覆盖独立工作区与首页默认助手，不使用预设回答替身。三个临时账号均清理，删除后访问返回 410。
- 6 个离线故障构造检查，包括空输出、失败恢复及残留调用限制。此类构造只证明代码缺口，不代表供应商实际返回过所有异常格式。
- 现有后端回归 188 项通过，2 条依赖弃用警告。原测试目录未发现 Monid 专项测试，故不能以这 188 项替代外部接口验收。
- 没有执行 iOS 界面或真机操作；本轮验证对象是后端适配及真实 Agent 编排。单次测量和小样本不能作为稳定性百分比或性能承诺。

精简原始记录：[EVIDENCE.json](EVIDENCE.json)。本机完整脚本、隔离数据库和日志在 `.build/monid-audit/`；不包含生产用户数据或服务密钥。

## 基础能力

| 能力 | 结果 | 具体边界 |
|---|---|---|
| 默认搜索、Google、百度 | 成功 | 返回可保存和引用的摘要，单次约 6–12 秒；不是全文 |
| Bing | 复测成功 | 首次连接失败并未拿到运行 ID；另一查询约 5 秒成功，服务器约 4 秒成功。不能据此证明首次请求没有提交，未自动重发原请求 |
| Reddit 搜索 | 成功 | 约 6 秒取得帖子链接与短摘要 |
| YouTube、微信、B站搜索 | 成功 | 都能取得真实搜索结果；不等于取得字幕、评论或完整文章。微信样本包含多年前文章，不能直接称为最新动态 |
| Amazon 与 LinkedIn 招聘 | 公开搜索可用 | 得到 Amazon 商品／直播评测及 LinkedIn 岗位链接；未验证完整评价列表、评论分页或岗位有效状态，不作为专门平台抓取通过 |
| 普通官网正文 | 成功 | Anker 商城、集团官网、about-us 均有成功；接口约 4 秒。404 页面正确拒绝作为正文 |
| Reddit 正文 | 当前链路不可用 | Firecrawl 对测试帖子明确返回 HTTP 403，理由是不支持该站点；本机和服务器都复现，不是仅 Mac 代理问题 |
| PDL 公司档案 | 已知公司成功 | Anker Innovations 和 Stripe 约 3–4 秒成功，返回匹配字段；仍须按候选档案与官网核对 |
| PDL 无匹配公司 | 业务失败被错误处理 | 实际响应是带运行 ID 的 404，无匹配且计费为 0；当前 App 适配却归为服务不可用 |
| 视频字幕 | 有效链接成功 | 同一评测视频短链及完整链接均成功，约 8 秒；取得约 1.5 万字符英文字幕，Agent 能继续逐段读取 |
| 缓存 | 成功但策略粗 | 同一公开搜索在新任务中复用，新增供应商记录 0，约 0.01 秒；缓存统一 24 小时，没有用户可表达的强制刷新参数 |
| 最近一个月过滤 | 参数调用成功 | 接口接受 time_range=month 并返回结果；本轮没有逐条核实文章日期，不能视为严格时效保证 |

最初字幕失败用例误填了少一位的视频 ID；这是本轮测试输入错误，已纠正并用有效 ID 验证，不能计作供应商字幕故障。无效 ID 在发给供应商之前也缺少本地格式校验。

| 公司重名、不确定身份 | 搜索候选后集中询问一次，约 23 秒 | 合理，没有直接猜定公司 |

| 首页：联网并保存，未说明自己的产品 | 只查询本地，然后询问产品类型，约 198 秒 | 补问本身可以理解，但没有先完成明确要求的官网读取，且等待过长 |
| 首页：已说明 SaaS 产品、对象、目标和网址 | 只查询本地并保存准备包，约 66 秒；外部来源数 0 | 未满足先联网要求，虽然后台标记 completed。本轮未留存报告正文，不能进一步断言是否在正文中说明了未联网 |

这些时间包含模型和多步工具等待，不能直接归因于 Monid 或网络。实际接口采集通常比整体 Agent 任务短得多。

## 原因与建议优先级

### P1：准备流程和公司调研没有组合起来

证据：

- `backend/skills/communication_prep/SKILL.md` 仍写“自动调研尚未接通”。
- 对应 `skill.json` 的 allowed_tools 没有 search_company/read_source/enrich_company/get_video_transcript，也没有 run_skill；`_skill_context` 会严格按该表过滤。
- 首页准备任务会自动加载 communication_prep，因此无法调用联网工具，也不能再切换流程。
- company_research 的工具表反过来没有 save_preparation，且不能再加载其他流程；只靠单一排他 Skill 容易使调研与保存相互断开。
- 独立工作区没有同样的自动加载路径，导致相同需求因入口不同表现不同。

建议：让准备流程按需调用所需调研能力，并保留保存动作；独立工作区与首页使用一致调度。更新失效说明和摘要。无需用户手选 Skill，也不要每次准备都强制调研。

同时，初始 Skill 索引只向模型提供名称／说明／available，run_skill.inputs 又只是任意字符串字典，没有让模型获知具体流程允许的字段。实际离线准备场景发生两次 SKILL_INPUT_INVALID。应提供精确输入规范或改为服务端整理输入；错误应告诉模型要修哪个字段，而非重复盲猜。

### P1：错误响应中的运行 ID 和业务原因被丢弃

直接观察 `/v1/run`：Reddit 返回 HTTP 403、PDL 无匹配返回 HTTP 404，JSON 均带 runId、COMPLETED、providerResponse 和零费用回执。当前 `Monid.request` 在解析 JSON 前就拒绝非 2xx，导致本地停留 submitting、external_id 为空，后续错误又被 ToolRegistry 统一变成“未找到可访问资料”。

建议：先安全解析结构化响应；有合法 runId 就持久化回执，再区分不支持站点、没有匹配、限流、鉴权和网络中断。403 不支持站点应立即停止这条路径；空搜索或公司无匹配应作为可解释的空结果。没有回执的网络中断继续保留未知状态，不能盲目重复提交。

### P1：继续任务会复用终态失败结果

离线构造真实存储与适配器检查：第一次得到终态供应商 503 后，再执行同任务同参数，不产生 POST 或 GET，直接取回同一失败结果。用户点继续也无法重新推进。

建议：成功回执可复用；运行中回执继续查询；确定失败的可重试请求由明确的新执行尝试处理。未知提交必须先核对已有运行，不把它和明确失败混成一类。为这些状态补专项回归。

### P2：输出质量、新鲜度与无效尝试

- 公司输出为 null、空对象或应用层错误对象时，当前代码会将 JSON 字符串存成“公司档案”。这三项是故障注入复现；真实已知公司正常成功。应校验非空档案及关键字段，避免垃圾资料入库。
- 读取结果 success=false 时只返回空 items，没有明确页面失败原因；应与确实没有相关内容区分。
- 24 小时统一缓存不适合“最新动态”。增加按类型有效期与明确刷新语义，保留实际抓取日期，不把缓存复用日期当作更新日期。
- Reddit 应对已确认不支持的正文抓取立即降级，或后续接一个实测可用的 Reddit 正文接口。降级说明保留，减少重复失败及同一片段的重复引用。Amazon、微信、B站也不能只凭搜索成功宣传完整评论／字幕能力。
- PDL 只在确实需要公司规模、行业、成立时间等字段且身份已定位时补充；本次门店 SaaS 准备中额外调用了 PDL，未见它帮助完成保存。
- `backend/adapters/monid.py` 仍有每任务 20 次调用上限。这是上轮去掉 Agent 次数限制时遗漏的独立限制，应按此前明确要求一并取消，保留进展检测与取消。

## 建议的自然触发规则

1. 普通表达、复盘、已有资料问答，优先本地；明确不要联网就不联网。
2. 用户要求调研、近期动态、竞品、公开反馈，或者准备需要核实外部事实时，自动调用所需调研能力。
3. 用户提供准确网址，优先读取该网址；没有必要就不追加搜索或公司数据库。
4. 公司身份确实不清楚时集中询问一次，避免后续反复确认。
5. 已有资料足够且时效合适时复用；用户明确要刷新或最新动态时遵循新鲜度策略。
6. 以完整目标验收：要求“调研后保存”的任务，应同时检查外部读取结果与准备包提交；有缺口就清楚说明，不能只根据工具返回或任务 completed 宣称满足需求。

首轮修改建议只覆盖上述 P1，加上残留 20 次上限、基础输出校验和新鲜度语义；平台扩展随后按真实需求做，不需要先铺满 Monid 全目录。
