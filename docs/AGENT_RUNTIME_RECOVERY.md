2026-10-14，本地分支 `fix/agent-runtime-recovery`，基于已合并的 PR #1。仅调整 Skill 预算、业务任务调度和归档分段恢复；模型、服务商和交互选择沿用已确认方案。

## Skill 预算

- 普通聊天及沟通准备、复盘、记忆草稿：最多 4 轮、12 次工具调用。公司调研加载后采用 8 轮、20 次工具调用及对应上下文预算。这些数字包含加载流程本身，属于任务总数，不是每次加载新增额度。
- `runtime.json` 的 `task_limits` 设定所有流程的总上限：8 轮、20 次工具调用，每次执行期限 600 秒。加载 Skill 不延长本次执行期限；手动继续仍使用一次新的执行期限。
- 任务保存各预算配置快照、活动预算及累计用量。模型轮次和工具调用在执行前持久化预留；失败、切换 Skill、等待用户、取消后继续和后端重启均不重置累计次数。
- 工具预算用完后关闭工具，让剩余模型轮次整理回答。总轮次已用完的任务需要发送新消息；不靠无限重试扩大额度。
- 手动继续恢复原任务的预算配置；若加载流程发生在尚未保存整轮结果之前，会补回对应流程正文。运行版本更新为 `agent-runtime@10-recovery`，更早运行版本的未完成任务按既有依赖校验规则要求重新发送。

## 业务调度

- TTS 使用 1 个独立工作线程；精转写、录音资料整理和归档共用原有 2 个后台工作线程。长时间等待 ASR 供应商不会占用 TTS 的执行名额。
- 只为实际可用名额提交任务，不把所有排队任务提前塞入线程池。任务在工作线程开始处理时才从 `queued` 改成 `running`。
- 同一通道按提交时间排列。取消的旧执行在真正退出前仍占用名额；同一任务的新尝试等旧尝试退出，避免前后版本同时处理。队列和重启后手动继续沿用原有持久状态。

## 归档分段恢复

- 每段返回后，先验证结构、长度、来源和逐字引用，再把候选结果保存到任务的 `archive_checkpoint`。最终个人记忆仍在完整归档完成后统一写入。
- 分段标识绑定正文、来源版本、当前范围、本人身份、归档授权、空间目标及模型/提示词版本。失败、取消或重启后，用户手动继续时只复用完全匹配的已完成分段；过期分段重算，撤下的资料不写入。
- 每段处理前后及最终写入前重新核对归档输入。最终核对与记忆写入在同一数据库事务中，防止资料修订或关联变化与写入竞态。恢复后再归档产生新的授权，旧归档任务不能代替新任务继续。
- 相同候选内容去重；用户改过或撤回的同一候选不会被重试覆盖、重新启用。归档的排队、执行、停止、失败和重启中断状态同时反映到空间。
- 只承诺复用已经成功保存的分段。模型返回前或保存前进程中断的那一段，手动继续仍可能再次调用模型并产生费用。
